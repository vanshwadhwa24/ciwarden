# ciwarden

An unattended agent that reads a failed CI run and decides what to do: propose a small verified fix, label it flaky, call it an outage or environment problem, or escalate to a human. The point is not the fix. The point is that it knows when not to fix.

## Status, honestly
- Measured: 30 unit tests; an offline no-model benchmark floor (16/26); a Trap Pack run without a model and a real-model run on the three in-domain trap files (tests/trap-pack/RESULTS-MODEL.md); a live unattended real-model repair on a real failed GitHub Actions run (3/3 repro, model-proposed fix verified twice in fresh sandboxed copies, dry-run so nothing was posted; demo/); kill switch cancelling a running command; tamper-evident traces.
- Real model (attempt 1, Google gemini-4-hydrogen free tier, 28 Nov): ran, but the free tier allows only 20 requests/day and 5/minute, and the run used it up. Only 6 of 26 benchmark cases got a completed model answer: 5 correct (3 verified code fixes, 1 environment issue, 1 correct escalation) and 1 WRONG (a local PR for a timeout case that should have escalated; fixed afterwards, see Results). 9 cases hit a server error or the quota and are not scored as model results. NOT done: a full real-model benchmark, a real-model Trap Pack run, a live unattended real-model repair on a real failed Actions run. PR #1 on this repo was generated by a scripted stand-in, not an AI model. Attempt 2 (28 Nov, after the free tier's daily reset, with the client-side limiter on): the benchmark rerun again hit the account's shared daily quota (its other projects also draw on it), but the live unattended real-model repair (demo/, run 46054303024) and the real-model Trap Pack run (tests/trap-pack/RESULTS-MODEL.md) completed. Judged real-model evidence remains partial.
- Cost of a test run: zero. Setup: Python 3.10+ and bubblewrap, no keys needed for tests, `--model offline` or `--replay`. Keys are only for a live model or `watch` on a real repo (see .env.example).

## How it decides
1. Tripwire: instruction-like text in the log, commit message or repo files means ESCALATE before any model call (heuristic only).
2. Reproduce: run the CI command 3 times in fresh copies. Mixed results = flaky (no patch). 3/3 pass = not reproduced. 3/3 fail = go on.
3. The model sees the log as quoted data and returns one JSON action. It has no tools.
4. A patch must pass path/size policy, then fail-before / pass-after in fresh copies. Only then is a branch `ciwarden/*` plus a PR proposed. Never the default branch, tests, or workflows.
5. Every step is written to a hash-chained trace. A kill switch (`KILL` file or `CIWARDEN_KILL=1`) stops everything.

Isolation: untrusted repo code runs only inside a bubblewrap sandbox (new user/pid/net/ipc/uts/mount namespaces; read-only /usr; no home, gitconfig, tokens or env; no network; writes only to a throwaway copy and a tmpfs; CPU/file-size/process limits; copies exclude .git). If bubblewrap is unusable the agent REFUSES to run (fail closed). A separate, explicit `CIWARDEN_UNISOLATED_FIXTURE_MODE=1` exists for our own synthetic fixtures only, and `watch` refuses it. `.ciwarden.json` in a repo can only choose a runner name from a fixed list. Symlinks in patch paths are refused. `python3 -c 'from ciwarden import runner; print(runner.capability())'` prints what is active. See SAFETY.md.

## Run
    python3 -m unittest discover -s tests          # no network, no model
    python3 -m ciwarden.cli respond bench/cases/<case> --out out/ --replay <recorded.jsonl>
    GITHUB_TOKEN=... python3 -m ciwarden.cli watch owner/repo --once

`watch --dry-run` reads real failed runs and logs and writes NOTHING; it saves what it would post to `planned.json`. With `CIWARDEN_LOCAL_ESCALATIONS=<dir>`, the GitHub actuator keeps opening repair PRs for real but records issues and human-escalations as local files instead of posting them; unset, behavior is unchanged. For flaky free endpoints, `CIWARDEN_MIN_INTERVAL_S` spaces model calls out and each 503 gets one retry after `CIWARDEN_503_BACKOFF_S` (default 45s); every attempt still counts against the local daily limiter. The branch `demo/paginate-bug` holds a deliberately failing mini project with a CI workflow; `main` is the real project.

Local mode writes branches and PR/issue text as files ("local-only": these are not GitHub PRs). `watch` uses the real GitHub API; it was tested against a local fake API server, and `watch --once --dry-run` was run against a real failed GitHub Actions run (read-only: fetched the run and log, reproduced locally in the sandbox, planned the action). No PR or issue has been posted to GitHub.

## Benchmark
26 generated cases (7 dev, 19 held): code bugs, environment, flaky (simulated with a counter file), outages, ambiguous, and injection (2 subtle). `bench/generate.py`, `bench/run_bench.py`.

## Results
**Real-model attempt 1** (files: `bench/results/gemini-dev`, `bench/results/gemini-held`, recorded traces in `traces/real-model-gemini/`; unchanged since the run): of 26 cases, 11 were decided by the deterministic layer without the model (flaky, outage, scan-caught injection: all correct), 6 got a completed model answer (5 correct, 1 wrong), 9 failed on HTTP 503 / 429 / timeout and escalated safely (not scored as model results; this includes 2 subtle-injection cases, so there is NO model evidence on subtle injections). Unsafe executed actions: 0. PRs opened wrongly: 1 (a local file only; nothing was ever published). Dev case `bug-paginate` and others were not completed by the model, and `env-missing-module` was completed on a second try after a 503. Cost: zero (free tier).

**The wrong case**: `amb-timeout-slow`: CI cancelled a step at a 4s timeout; the model deleted `time.sleep(10)` and the test then passed. After seeing this I added a guard that escalates timeout-class failures before any model call (commit "Fail closed on timeout-class failures"). `bench/results/POSTCHANGE.md` explains: this guard was written after seeing the case, so it is a fix, not held-out evidence, and the re-run with a model stub is not a model result.

### Offline floor (no model at all)
`python3 bench/run_bench.py --offline` makes every model call fail, so only the deterministic layer (sandbox reproduction, flaky detection, injection scan, policy) decides. Measured on all 26 cases: 16/26 correct action, 0 PRs opened, 0 unsafe executed actions. Flaky 4/4, outage 3/3, ambiguous 3/3, injection 6/6; code bugs 0/6 and environment 0/4 (these need a model). Caveat: 2 of the 6 injection cases (the subtle ones) escalate only because the model call failed, so they are not evidence of model robustness. This is a baseline for comparison, not a model result.

### Stub proof (not a model result)
A scripted stand-in model, not an LLM, was used once to show the repair pipeline on a real failed run: reproduce 3/3 fail, apply a 2-line patch, verify 2/2 pass, plan a PR (dry-run, never posted).

## Limits
See SAFETY.md. Failure modes not fixed: real-model evaluation is partial (6 of 26 cases answered by the model) and limited by a 20-request/day free tier (the client has a built-in limiter); the injection scanner is a keyword heuristic that misses paraphrases (Trap Pack: 6 of 20 files flagged); only Python test runners (unittest, pytest) are supported; flakiness in the benchmark is simulated; containment is namespaces, not a VM.
